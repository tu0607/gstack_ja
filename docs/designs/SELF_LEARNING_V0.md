2026-03-28 に /office-hours + /plan-ceo-review + /plan-eng-review によって生成

リポジトリ: gstack
ステータス: ACTIVE
モード: オープンソース / コミュニティ

## 問題の定義

GStack は 30 以上のスキルをセッションをまたいで実行しますが、セッション間で何も学習しません。/review セッションが N+1 クエリのパターンを見つけても、同じコードベースの次の /review はゼロから始まります。/ship の実行でテストコマンドを発見しても、将来のすべての /ship はそれを再発見します。/investigate が厄介な競合状態を見つけても、以後のどのセッションもそれを知りません。

これはどの AI コーディングツールにも共通の問題です。Cursor にはユーザー単位のメモリがあります。Claude Code には CLAUDE.md があります。Windsurf には永続的なコンテキストがあります。しかしどれも積み上がりません。学習内容を構造化せず、スキルの間で知識を共有しません。

## 作るもの

プロジェクト単位の組織的な知識を、セッションとスキルをまたいで積み上げていきます。型付きで信頼度がスコア化された学習内容を、すべての gstack スキルが読み書きできるようにします。目標は、同じコードベースで 20 セッション後には、gstack がすべてのアーキテクチャ上の決定、過去のバグのパターン、そして自分が間違っていた時を把握していることです。

## 北極星

/autoship(リリース 5)。1 つのコマンドで、フルのエンジニアリングチームが動きます。機能を説明し、計画を承認すれば、残りはすべて自動で進みます。/autoship は、学習(R1)、レビューの品質(R2)、セッションの永続化(R3)、適応的な儀式(R4)がなければ成り立ちません。リリース 1〜4 は、/autoship を実際に機能させるためのインフラです。

## 対象ユーザー

YC の創業者で、AI を使って開発している人たちです。gstack を実際のコードベースで週に 20 回以上動かし、同じ質問を二度してくることに気づく人です。

## 差別化

| ツール | メモリのモデル | スコープ | 構造 |
|------|-------------|-------|-----------|
| Cursor | ユーザー単位のチャットのメモリ | セッション単位 | 非構造化 |
| CLAUDE.md | 静的ファイル | プロジェクト単位 | 手動 |
| Windsurf | 永続的なコンテキスト | セッション単位 | 非構造化 |
| **GStack** | **プロジェクト単位の JSONL** | **セッションとスキルをまたぐ** | **型付き、スコア付き、減衰する** |

## 状態を保存するシステム

gstack には 4 つの異なる永続化レイヤーがあります。保存のパターン(`~/.gstack/projects/$SLUG/` の JSONL)は共通ですが、目的が異なります。

| システム | ファイル | 保存する内容 | 書き込み元 | 読み取り元 |
|--------|------|---------------|------------|---------|
| **学習** | `learnings.jsonl` | 組織的な知識(落とし穴、パターン、好み) | すべてのスキル | すべてのスキル(プリアンブル) |
| **タイムライン** | `timeline.jsonl` | イベントの履歴(スキルの開始/完了、ブランチ、結果) | プリアンブル(自動) | /retro、プリアンブルのコンテキスト復旧 |
| **チェックポイント** | `checkpoints/*.md` | 作業状態のスナップショット(決定、残作業、ファイル) | /checkpoint、/ship、/investigate | プリアンブルのコンテキスト復旧、/checkpoint の再開 |
| **ヘルス** | `health-history.jsonl` | コード品質のスコアの推移(ツールごと、総合) | /health | /retro、/ship(ゲート)、/health(傾向) |

これらは互いに重なりません。学習 = 何を知っているか。タイムライン = 何が起きたか。チェックポイント = 今どこにいるか。ヘルス = コードがどれだけ良いか。それぞれ異なる問いに答えています。

## リリースのロードマップ

### リリース 1: 「GStack が学ぶ」(v0.13-0.14) — 出荷済み

**見出し:** すべてのセッションが次のセッションを賢くする。

出荷した内容:
- `~/.gstack/projects/{slug}/learnings.jsonl` への学習の永続化
- 手動でのレビュー、検索、整理、エクスポート用の `/learn` スキル
- すべてのレビュー指摘への信頼度の調整(1〜10 のスコアと表示ルール)
- observed/inferred の学習に対する信頼度の減衰(30 日ごとに 1 ポイント)
- プロジェクトをまたぐ学習の発見(オプトイン。AskUserQuestion による同意)
- レビューが過去の学習と一致したときの「学習が適用されました」の表示
- /review、/ship、/plan-*、/office-hours、/investigate、/retro への統合

スキーマ:
```json
{
  "ts": "2026-03-28T12:00:00Z",
  "skill": "review",
  "type": "pitfall",
  "key": "n-plus-one-activerecord",
  "insight": "Always check includes() for has_many in list endpoints",
  "confidence": 8,
  "source": "observed",
  "branch": "feature-x",
  "commit": "abc1234",
  "files": ["app/models/user.rb"]
}
```

種類: `pattern` | `pitfall` | `preference` | `architecture` | `tool`
ソース: `observed` | `user-stated` | `inferred` | `cross-model`

アーキテクチャ: 追記のみの JSONL。重複は読み取り時に解決されます(キーと種類ごとに「最新が勝つ」)。書き込み時の変更はなく、競合状態もありません。

### リリース 2: 「Review Army」(v0.14.3-0.14.4) — 出荷済み

**見出し:** すべての PR に 10 人の専門レビュアー。

出荷した内容:
- 7 つの並列の専門サブエージェント: 常時(テスト、保守性)+ 条件付き(セキュリティ、パフォーマンス、データ移行、API 契約、デザイン)+ レッドチーム(大きな差分や重大な指摘のとき)
- 信頼度付きの JSON 構造の指摘と、エージェント間のフィンガープリントによる重複排除
- レビューごとに記録される PR の品質スコア(0-10)と、/retro での推移
- 学習を踏まえた専門家プロンプト。過去の落とし穴を分野ごとに注入
- 複数の専門家の合意のハイライト。確認された指摘はブーストされる
- PLAN_COMPLETION_AUDIT による、強化された Delivery Integrity
- チェックリストの再構成: CRITICAL カテゴリはメインのパスに残し、専門カテゴリは review/specialists/ の専用チェックリストに切り出す

### リリース 2.5: 「Review Army の拡張」 — 未出荷

**見出し:** R2 が安定してから出荷する。コアのループの動きを確認する。

事前確認: R2 の品質指標(PR の品質スコア、専門家のヒット率、誤検知率、E2E テストの安定性)を確認します。コアのループに問題があれば、まずそれを直します。

出荷する内容:
- E1: 適応的な専門家のゲート。過去の実績が 0 件の指摘の専門家を自動的にスキップします。プロジェクトごとのヒット率を gstack-learnings-log で保存します。ユーザーは --security などで強制できます。
- E3: テストのスタブの生成。各専門家が指摘と一緒に TEST_STUB を出力します。フレームワークはプロジェクトから検出します(Jest/Vitest/RSpec/pytest/Go test)。Fix-First に流れ込み、AUTO-FIX は修正を適用し、テストファイルを作成します。
- E5: レビューをまたぐ指摘の重複排除。gstack-review-read で過去のレビュー記録を読みます。ユーザーがスキップした過去の指摘に一致する指摘は抑制します。
- E7: 専門家ごとのパフォーマンス追跡。gstack-review-log で専門家ごとの指標を記録します。タイムラインとの統合: 専門家の実行は timeline.jsonl に現れ、/retro で推移を見られます。

### リリース 3: 「Session Intelligence」(v0.15.0) — 出荷済み

**見出し:** AI のセッションが、何が起きたかを覚えている。

出荷した内容:
- セッションのタイムライン: すべてのスキルが開始/完了のイベントを `~/.gstack/projects/$SLUG/timeline.jsonl` に自動で記録します。ローカルのみで、どこにも送信されません。テレメトリーの設定にかかわらず常に有効です。
- コンテキストの復旧: コンパクション後やセッション開始時に、プリアンブルが最近の CEO プラン、チェックポイント、レビューを一覧にします。エージェントは最新のものを読んでコンテキストを復旧します。
- セッションをまたぐ注入: プリアンブルは、現在のブランチについて LAST_SESSION と LATEST_CHECKPOINT を表示します。入力する前に、どこまで進んだかが分かります。
- 予測的なスキルの提案: 直近 3 セッションが一定のパターン(review、ship、review)に従っていれば、次に欲しそうなスキルを提案します。
- セッション開始時の「おかえりなさい」という、合成されたコンテキストのメッセージ。
- `/checkpoint` スキル: 作業状態のスナップショットの保存、再開、一覧。Conductor のワークスペースの引き継ぎのために、ブランチをまたいで一覧できます。
- `/health` スキル: 既存のプロジェクトのツール(tsc、biome、knip、shellcheck、テスト)をラップするコード品質のスコアキーパー。0-10 の総合スコア、推移の追跡、スコアが下がったときの改善の提案。
- タイムラインのバイナリ: `bin/gstack-timeline-log` と `bin/gstack-timeline-read`。
- ルーティングのルール: /checkpoint と /health をプリアンブルのスキルのルーティングに追加。

設計ドキュメント: `docs/designs/SESSION_INTELLIGENCE.md`

### リリース 4: 「Adaptive Ceremony」 — 未出荷

**見出し:** GStack は、安全を損なわずに、あなたの時間を尊重する。

儀式(ceremony)と信頼(trust)は別の関心事です。儀式とは、PR が通過するレビュー/テスト/QA のステップの集合です。信頼とは、どの儀式のレベルを適用するかを決めるポリシーエンジンです。両者は互いに影響し合いますが、一つにはなりません。

出荷する内容:

**儀式のレベル:**
- FULL: すべての専門家、敵対的レビュー、Codex の構造化レビュー、カバレッジの監査、プラン完了の確認。大きな差分、新機能、移行、認証の変更向け。
- STANDARD: 敵対的レビュー + Codex、カバレッジの監査、プラン完了の確認。中規模の差分、一般的な機能開発向け。
- FAST: 敵対的レビューのみ。小さく、テストが十分な変更で、信頼できるプロジェクト向け。

**信頼のポリシーエンジン:**
- スコープを意識した信頼。信頼は全体ではなく変更の種類ごとに得られます。ドキュメントのみの PR で良い履歴があっても、移行の PR に対する信頼は得られません。
- 変更の種類の検出: docs、tests、config、frontend、backend、migrations、auth、infra。種類ごとに独自の信頼の閾値があります。
- 信頼のシグナル: 種類ごとの連続したクリーンなレビュー、/health スコアの安定性、回帰の頻度、テストカバレッジの推移。
- 信頼は決して早送りされません: 移行、認証/権限の変更、新しい API エンドポイント、インフラの変更。これらは信頼のレベルに関係なく、常に FULL の儀式になります。
- 二値のリセットではなく、段階的な低下。1 回の回帰で、すべての信頼がリセットされることはありません。その変更の種類について信頼が 1 段階下がるだけです。

**スコープの評価:**
- /review、/ship、/autoplan で、差分の大きさ、触れたファイル、変更の種類に基づく TINY/SMALL/MEDIUM/LARGE の分類。
- 儀式のレベル = f(スコープ、信頼、変更の種類)。

**TODO のライフサイクル:**
- 受け付けた TODO を対話的に承認する /triage
- 並列エージェントによる一括解決の /resolve

### リリース 5: 「/autoship — 1 つのコマンドで、機能をまるごと」 — 未出荷

**見出し:** 機能を説明する。計画を承認する。残りはすべて自動。

/autoship は、直線的なパイプラインではなく、再開可能なステートマシンです。レビューと QA は作業をビルド/修正へ差し戻すことができます。コンパクションはどのフェーズでも割り込む可能性があります。システムは、それらから穏当に回復しなければなりません。

```
                    ┌──────────┐
                    │  START   │
                    └────┬─────┘
                         │
                    ┌────▼─────┐
                    │ /office- │
                    │  hours   │
                    └────┬─────┘
                         │
                    ┌────▼─────┐
                    │/autoplan │ ◄── single approval gate
                    └────┬─────┘
                         │
              ┌──────────▼──────────┐
              │       BUILD         │ ◄── /checkpoint auto-save
              └──────────┬──────────┘
                         │
              ┌──────────▼──────────┐
              │      /health        │ ◄── quality gate
              │   (score >= 7.0)    │
              └──────────┬──────────┘
                         │ fail → back to BUILD
              ┌──────────▼──────────┐
              │      /review        │
              └──────────┬──────────┘
                         │ ASK items → back to BUILD
              ┌──────────▼──────────┐
              │        /qa          │
              └──────────┬──────────┘
                         │ bugs found → back to BUILD
              ┌──────────▼──────────┐
              │       /ship         │
              └──────────┬──────────┘
                         │
              ┌──────────▼──────────┐
              │ /checkpoint archive │ ◄── preserve, don't destroy
              └─────────────────────┘
```

出荷する内容:
- 上の状態機械による /autoship の自律パイプライン。
  各フェーズは timeline.jsonl に書き込みます。チェックポイントは各フェーズの前に自動保存されます。
  コンパクションからの復旧: コンテキストの復旧はチェックポイントとタイムラインを読み、最後に完了したフェーズから再開します。
- 完了時のチェックポイントのアーカイブ(削除ではない)。失敗した autoship の実行をデバッグできるように、復旧の状態は保存されます。
- /ideate ブレインストーミングのスキル(並列の発散的なエージェント + 敵対的なフィルタリング)
- /plan-eng-review の調査エージェント(コードベースの分析者、履歴の分析者、ベストプラクティスの調査者、学習の調査者)

依存関係: R1(調査エージェントのための学習)、R2(品質のためのレビュー軍)、R3(永続化のためのセッションの知性)、R4(速度のための適応的な儀式)。

## リスク登録簿

### 指標を、精査を省く許可として扱うこと
(2026-04-01 の Codex レビューで特定)

/health のスコア、クリーンなレビューの履歴、タイムラインのパターンは有用なシグナルです。しかし、安全の証明ではありません。それらのシグナルが儀式の削減と /autoship の両方に供給されると、起きる失敗は、まれで、気づきにくく、影響の大きなミスです。緩和策:
- 特定の変更の種類は決して早送りされません(移行、認証、インフラ、新しいエンドポイント)。
- 信頼は、二値のリセットではなく段階的に低下します。
- /autoship は、プロジェクトごとの最初の実行では常に FULL の儀式を行います。信頼は実績によって得られます。

### 古いコンテキストの復旧
(2026-04-01 の Codex レビューで特定)

コンテキストの復旧は、間違ったブランチの状態、古くなった計画、無効なチェックポイントを注入する可能性があります。緩和策:
- チェックポイントは YAML のフロントマターにブランチ名を含みます。コンテキストの復旧は、現在のブランチで絞り込みます。
- タイムラインの grep は、LAST_SESSION を表示する前にブランチで絞り込みます。
- 古いアーティファクトの検出: チェックポイントが 7 日より古ければ、現在の状態として提示するのではなく、古い可能性があると注記します。

### 必要な検証指標
(2026-04-01 の Codex レビューで特定)

リリース 4(適応的な儀式)の出荷前に、次を測定します:
- 予測的な提案の精度(ユーザーは提案されたスキルを実行したか)
- 信頼のポリシーの誤スキップ率(早送りされた PR に、マージ後の問題が出たか)
- コンテキスト復旧の精度(復旧されたコンテキストは、実際の状態と一致したか)
- /health のスコアと実際のコード品質の相関(高いスコアは、本番のバグの少なさを予測するか)

これらの指標は、R3 の利用中に収集し、R4 を出荷する前に確認すべきです。

## 認めた影響元

自己学習のロードマップは、Nico Bailon による [Compound Engineering](https://github.com/nicobailon/compound-engineering) プロジェクトのアイデアに着想を得ています。学習内容の永続化、並列のレビューエージェント、自律パイプラインについての彼らの探求が、GStack のアプローチの設計のきっかけになりました。私たちは、それらのコンセプトを直接移植するのではなく、GStack のテンプレートシステム、語り口、アーキテクチャに合うように適応させました。
