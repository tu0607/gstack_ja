## 実装計画

### 背景

2026-10-06 のトリアージでは、10月3日のウェーブのトリアージ以降に開かれた issue と PR をすべて対象にしました(#3018 から #3052、および #3012 と #3016)。以下の主張はすべて、プローブの実行またはコードの読解によって main に対して検証しています。コントリビューターのコードは根拠としてのみ読みました。コントリビューターのブランチからは何もマージしません。各修正は、その診断または設計を使ったコントリビューターへの `Co-authored-by` クレジットとともに書き直します。

重大な項目は、2つのパターンを共有しています。

1. **実際のユーザーを壊すシェルの前提。** 読み込まれるヘルパーは bash を前提にしていますが(macOS の既定は zsh で、Claude Code の Bash ツールも zsh で動きます)、返信テンプレートは信頼できないテキストを二重引用符の中に入れており、そこではバッククォートがコマンドとして実行されてしまいます。
2. **失敗が間違った原因として報告される。** Codex の利用上限が「結論が出ない。続行します」と表示され、大きすぎる autoplan のジャーナルがリトライ可能な識別失敗と表示され、シェルで組み立てた autoplan の init が「init が見つからない」と表示され、Windows の `browse chain` がパイプ入力を受けたのに何も実行せず終了コード 0 で終わります。

### リリースの約束(完了の基準)

- **P1. Codex の外部レビューは zsh から動作する。** 読み込まれる gstack のヘルパーはすべて、bash または zsh から source されたとき、どの作業ディレクトリからでも自分の場所を正しく特定します。無料テストは各ヘルパーを両方のシェルで source し、CI は zsh をインストールするので、そのテストが CI でスキップされることはありません。
- **P2. 信頼できないテキストは決してシェルとして実行されない。** 生成されたスキルは、レビュアーのテキスト、diff、エラーテキストを、二重引用符の中に入れてコマンドに渡しません。このパターンを検出する lint が失敗するようにします。
- **P3. すべての失敗は、実際の原因と実際の対処法を示す。** Codex のクォータ、大きすぎるジャーナル、シェルで組み立てた autoplan の init、Windows の chain 入力、Windows の Docker、Windows の browse の依存関係は、それぞれ修正の行を伴う具体的なメッセージを持ち、`docs/troubleshooting.md` または `docs/autoplan-guard-troubleshooting.md` に記載されます。
- **P4. 赤くなった有料 eval は、盲目的に再実行するのではなく、測定してから修正する。** /ship は(2026-10-05 に承認された)#3034 の測定してから修正するループを実行し、毎週の定期実行で赤くなった #3038 も同じループで修正します。

### Tier 1: 必ず出荷する

**A1. #3024: 読み込まれるヘルパーが zsh で壊れる(PR #3027, #3049, #3052)。** main でのプローブ: `zsh -c 'source bin/gstack-codex-probe && _gstack_codex_select_model exec'` は `Module not found "/../scripts/resolve-codex-generation-model.ts"` と `CODEX_MODEL: invalid` を表示します。そのため v1.91.16.0 以降、macOS の zsh での Codex の外部レビューはすべて `model_unusable` と報告されていました。`bin/gstack-egress-lib.sh` は zsh の下でそのディレクトリを呼び出し元の cwd に解決します(プローブ: `/tmp` を表示)。そのため、レシートと状態ルートがユーザーのプロジェクト内で探されていました。
- 修正: 単一の自己位置特定のイディオムを、source 時に一度だけ解決します。bash では `BASH_SOURCE[0]`、zsh では `${(%):-%x}`(bash がそれを解析しないよう `eval` の内側に置く)、それ以外は既定のインストールパスを使います。`bin/gstack-codex-probe`(5 か所)と `bin/gstack-egress-lib.sh` に適用します。`bin/gstack-paths` は source ではなく実行されるので、bash のシェバングの下で `BASH_SOURCE` を保持し、source されるヘルパーのガードの対象外とします。プローブの「source 時にコマンドを実行しない」というルールは維持します(パラメータ展開のみ)。
- 採用しなかった代替案: `$0`(#3049)は関数の中で読まれると関数名になり、`zsh -c` の下では `zsh` になるため採用しません。`functions_source`(#3027, #3052)は、バージョン対応ではなく簡潔さ(CEO-28)のために却下しました。
- クラスガード: 無料テストが、生成されたスキルが `source` または `.` で読み込むすべてのファイルを列挙します(手書きのリストではなく、レンダリングされた SKILL.md とセクションファイルから導出)。それぞれを無関係な cwd から bash と zsh の両方で source し、解決されたディレクトリと、ヘルパーごとに実際の呼び出し 1 回(モデルリゾルバ、状態ルート、egress ホーム)をアサートします。lint は、source されるヘルパー内で共有イディオム以外の `BASH_SOURCE` を検出すると失敗します。CI は無料レーンと Docker イメージに zsh をインストールし、`CI=true` の下では zsh がないとテストがスキップせず失敗します。
- クレジット: @marcosdetry(報告と診断)、@akshaykalia(egress-lib の発見)、@scottgigante-hubflow、@woodsonl、@bezdekt。

**A2. #3051: Codex の利用上限が「結論が出ない。続行します」と報告される。** コードの読解: `_gstack_codex_model_probe` はモデルと壊れたインストールのパターンしか照合しないため、クォータのエラーは `MODEL_PROBE_INCONCLUSIVE` に落ち、キャッシュされず、すべてのスキルで 30 秒ごとに再プローブされ、Codex 自身のメッセージとリセット時刻が失われます。
- 修正: 新しいプローブ結果 `quota_exhausted`(終了コード 4)を追加します。失敗した非タイムアウトの呼び出しで、Codex の利用上限の行と `insufficient_quota` の行に一致させます(単純なレート制限や HTTP 429 の行は、別の、キャッシュされない `rate_limited` 結果です。CEO-14 を参照)。Codex のエラー行をそのまま表示し、`CODEX_MODE: quota_exhausted` に対応付けます。すべての呼び出し元はそれを `unavailable`(カバレッジの欠落。決して合格扱いにしない)として扱い、その実行での残りの Codex 呼び出しをスキップします。`MODEL_UNUSABLE` と同じシグネチャで 15 分間キャッシュします。
- `lib/gate-outcomes.ts` に理由コード `quota_exhausted` と `rate_limited` を追加し、それぞれに `docs/troubleshooting.md` のアンカーを付けます。`classifyOutsideReview` は、レビューの stderr に含まれる同じ行を認識するので、実行中のクォータエラーは `unavailable (quota_exhausted)`、実行中の 429 は `unavailable (rate_limited)` と読まれます。
- テスト: issue から取った実際のメッセージを出力し終了コード 1 で終わるスタブの `codex` でプローブします。同じメッセージを出力して終了コード 0 で終わるスタブは `MODEL_OK` のままでなければなりません。タイムアウトは inconclusive の契約を保ちます。生成されたすべての preflight ブロックは `quota_exhausted` で分岐します。

**A3. #3046: 返信テンプレートがバッククォートをシェルとして実行する。** コードの読解: `review/greptile-triage.md:102,108` は `-f body="<reply text>"` を投稿し、下のテンプレートは本文に `` `<commit-sha>` `` と引用された diff のコードを入れます。二重引用符の中では bash が各バッククォートの範囲を実行します。`scripts/resolvers/preamble/generate-test-failure-triage.ts:74-75` も同様に、生のテストのエラー出力を `--body "..."` に入れています。

- **CEO-1(A6、無料スイートの不安定なテスト)。** #3034 の規定どおり、/ship の実行中に無料スイートのシャードが失敗すると、/ship はそのシャードの正確なファイル一覧(順序依存の失敗も捕捉する)を N 回(既定 10)、並列で、10 分の壁時計の上限の下で再実行します。ランナー自身の不安定テストのリトライはオフにし、リトライが測定される発生率を膨らませないようにします。これは、ワークフローの文言だけでなく、実行可能なランナーの変更が必要です。`scripts/ubicloud/test-free.sh` は現在 `GSTACK_FREE_RETRY_FLAKY=1` を無条件に設定しています。無料テストで、診断用のランチャーがリトライを無効にし、すべての結果を記録することを証明します。各再実行は独自の状態(一時的な HOME、一時的な状態ルート、独自のポート範囲)を持ち、最初の再実行はシャードの元の並列度でベースラインとして実行します。並列の再実行はそのようにラベルされ、それらが追加する競合を元の失敗と読まないようにします。`UBICLOUD_API_KEY` が設定され、プロジェクトが Ubicloud のテストコマンドを文書化している場合(gstack では `bun run test:ubicloud`)、再実行は 1 台の Ubicloud VM で N 個の並列プロセスとして実行します。そうでなければローカルで実行します。再実行はプロジェクトの文書化されたテストコマンドを、シャードのファイル一覧を引数にして使います。ランナーがファイル一覧を受け取れない場合は、失敗した全コマンドを再実行します。失敗を既存のものと呼んだり、push する前に、合格率と失敗のキャプチャを報告します。上限に達したら、部分的な件数を報告します(例: 10 件中 6 件完了)。これらの再実行は診断用とラベルされ、記録された判定を決して変えません。A6 の手順を固定する無料テストは、生成された ship スキルにおけるこのステップも固定します。
