# gate-diff の較正 — gstack の直近 50 件のマージ済み PR に対するツールの一覧

2026-10-10 に、`origin/main` の `20eb620`(v1.91.68.0)に対して `bun scripts/gate-diff-calibrate.ts --ref origin/main --count 50 --markdown` で生成しました。各コミットの first-parent の差分を、`gstack-gate-diff --commit <sha>` と同じ方法でスキャンしています。gstack は squash マージするため、first-parent の 50 コミットがそのまま着地した 50 件の PR です。クローンは shallow だったので、先に `git fetch --deepen=60 origin main` が必要でした(ツールは欠けた親を `GATE_ERROR=no_base … fix=git fetch --deepen` と報告します)。

## 測定するもの、しないもの

これは **ツールの一覧** です。すなわち、PR ごとに floor が挙げるハンク数、読み取り対象になる数、50 ハンク/200 KB の読み取り上限によって結果が部分的になる頻度、そして各タグが発火する頻度です。タグは事実上のラベルです(テストを、削除されたソースと一緒に削除した場合でも RH-1 になる)。そのため、タグの件数は問題の件数ではありません。

測定 **しない** もの: エージェントの指摘、採用/復元/未解決の処分、そしてレビュアーがタグ付きのハンクを読みたかったかどうか。設計にある 10 件の PR の手作業によるハンクの読み取りは、この表が裏付けるだけの人間の工程です。エージェントレベルのシグナルは、出荷後に保存されたレビュー記録から収集されます。計算のため、何も書き出しておらず、較正は状態のルートに触れません。

## 数値からの観察

- **PR ごとの一覧:** 中央値 40.5、75 パーセンタイル 267、最大 1,276(v1.91.8.0 のテスト監査の波)。対象になるものの中央値は 24.5。これは設計自身の測定(中央値 23〜45)と一致し、ハンクごとの処分は非現実的だと裏付けます。3 つのレベルが正しい単位です。
- **部分的な結果:** 20/50 の PR で読み取り上限に達しました。gstack のテストの多い PR では、「部分的(eligible の K 件を読んだ)」が例外ではなく一般的な状態になるでしょう。
- **RH-15(対、35 ハンク / 14 PR)** は検査してみると読みやすいものでした。実際の workflow の `timeout-minutes` の引き上げ、テストの `timeout 5000 -> 30000`、判定のしきい値 `4 -> 3`、正確な件数の検査を範囲に緩めたもの、そして緩和であるとラベルのついた締め付け。方向性のメモにより、読むのが速くなります。
- **RH-15?(対のない値):** 当初の仕様(「対のない値は RH-15? とタグ付けして読む」)では、848 ハンク / 41 PR でタグが発火しました。主に、新規または移動したテストのコードにおける `spawnSync(…, { timeout: 30_000 })` によるものでした。このリポジトリでは、同期的な spawn のすべてにタイムアウトが必要です(`test/spawnsync-timeout-tripwire.test.ts`)。そのため、ほぼすべてのテストの PR に数十のノイズのタグが付いていました。**決定(統合担当、設計の降格ルールに従う):** `RH-15?` は CI とランナー/lint の設定ファイルにのみ適用します。テストファイルでは、対のない値は一覧の情報にとどめ、対のある RH-15 のみをタグ付けします。この規則により、下の表には 13 件の PR にわたる 30 ハンクが出ていますが、すべて workflow かランナーの設定です。検出器も、キーと値の代入(`key: N`、`key = N`、`key(N)`、`--key N`、ネストした構造を開くゲートのキー)に絞り込み、`_` 区切りの数値リテラルにも対応しました。散文の文字列や `setTimeout` の呼び出しでは発火しなくなりました。
- **RH-1(411 ハンク / 18 PR):** そのうち 343 件はv1.91.8.0 のテスト廃止の PR のものです。29 件は skip/only のイディオムです(いくつかは条件付きの `process.platform === 'linux' ? describe : describe.skip`)。事実に基づくもので、その PR のレビュアーが欲しがる一覧そのものです。
- **RH-16(80 ハンク / 19 PR):** gstack の多くのベストエフォートな `catch {}` ブロック。設計が述べているとおり slop-scan と重なり、RH の ID の下に挙げています。
- **RH-12、RH-13、RH-14:** まれ(それぞれ 6 / 8 / 3 ハンク)で、検査すると妥当です。
- **RH-3 / RH-3?:** 発火しませんでした。この期間の gstack には `__snapshots__`/`.golden` の fixture がありません(SKILL.md のゴールデンは `.md` で、パスだけが挙がります)。
- 散文(`.md`、`.md.tmpl`)と生成・同梱されたパス(`dist/`、`vendor/`、ロックファイル、`.min.js`)は、floor の一覧のみに含めます。この規則がなければ、設計文書自身が、そこで説明するすべての RH の ID にタグを付けてしまったでしょう。
