# gstack 信頼性のフォローアップ(2026年10月4日): ヘッドルーム、正直な eval 判定、残りのホスト差分

## 実装計画

### 背景

ベース: origin/main `2db0b3adc`(v1.91.19.0、#3025)。深刻な問題の修正ウェーブ(severe fix wave)は、TODOS.md にフォローアップを残しました。このプランの根拠は、そのウェーブ用ブランチで行われた8回の定期センサス(37174266054 … 37198445662)です。

- 8回のセンサスのうち、緑(全合格)になったものは 0 回でした。判定の赤(red)は合計 21 件で、センサスごとに 2〜3 件でした。
- 原因別に見ると、10 件は検出器、スクリプト化されたアクター、または CEO モードの引き継ぎによるもの(1件ずつ修正中)、5 件は判定のサンプル数不足、3 件はプロバイダー起因の事象(ストリームの停止 1 件、拒否 2 件)、2 件はフィクスチャ/プロダクト、1 件はヘッドルームです。
- 失敗した 28 件のトライアルのうち 27 件が `assertion` とラベル付けされており、observer のタイムアウトも含まれています。つまり、レポート自体が実際に何が起きたかを誤って記述しています。
- 判定約 193 件のうち、赤になる率は約 1.2%(判定ごと)です。この率だと、全緑のセンサスになる確率は約 7% です。対策の対象は判定ごとの赤率であり、最大の原因はプロバイダー事象ではなく、壊れやすい検出器とスクリプト化されたアクターです。
- 最も遅いケースは plan-ceo-mode-routing の最大 687 秒、plan-mode-no-op の 613 秒です。ship-docsync-completion は予算の 88%、store は 79% を使っています。センサス全体の所要時間は 14〜15 分で、目標の約 10 分を超えています。review-army-perf(300 秒のうち 102〜140 秒)と plan-design-review-plan-mode(142〜240 秒、タイムアウトなし)は、ヘッドルームの問題ではありません。
- センサス 37198445662 では、アクショナビリティを採点する 21 件のワークフロー判定のうち 20 件がちょうど 4.00 で、5 を付けたものはありませんでした。文章の編集で低いサンプルは減らせますが、ルーブリックが 4 で頭打ちにしている平均を引き上げることはできません。

### リリースの約束

- **P0. センサスの赤を減らし、正直に報告する。** PR は、センサスごとに、マシンの分類別の判定の赤と、全緑になる確率の期待値を報告します。対象は、この PR 前の 8 回のセンサスと、この PR のすべてのセンサスです。繰り返し起きた赤の分類には、一回限りの表記修正ではなく、構造的な修正(リプレイ用コーパス、構造化されたシグナル、または高速化)があります。
- **P1. 最も遅いケースにヘッドルームを与える。** ヘッドルームレポートが、武装された予算の 75% を超えるとフラグを立てたケースは、作業量を減らして予算内に収めます。予算は引き上げません。週次の `eval:pass-rates --gate` のアラーム(コミット済みファイルに対する無料チェックではなく、コード変更で失敗しうるもの)は、85% を超えるケースにフラグを立てます。センサス全体の目標は 10 分なので、最も遅いゲートのスライスは今の 711 秒から約 450 秒まで下げる必要があります。
- **P2. ラベルは実際に起きたことを示す。** すべてのトライアル記録は、今と同じく `failure_class`(`assertion | contract | timeout | infra`。判定はこれを読みます)と 300 文字の `error` フィールドを維持します。さらに、任意で上限付きのフィールドを追加します。`failure_cause`(`contract`、`pre_turn_infra`、`api_error`、`refusal`、`provider_stall`、`session_timeout`、`observer_timeout`、`assertion`、`unknown`)、`failure_cause_evidence`、`failure_detail`(assertion は `{expected, received}`、判定は `{dimension, mean, samples, rationale}`。どちらも部分ごとに上限があります)です。機械には検出器の見逃しとプロダクトの問題を区別できないので、`detector` という原因は設けません。それは人が書く診断です。判定の出力(`panelVerdict`、`collector-outcomes.json`、レーンの終了コード、INFRA の再実行の対象になるかどうか)は EVAL_POLICY v1 のもとで同一に保たれます。これは、main と本ブランチの判定コードを 8 件のベースラインセンサスの成果物に対して実行し、凍結した v1 リーダーを新しい記録に対して実行することで証明します。この PR は v1 のもとで判定されます。
- **P2b. 赤は証拠と次の行動を指し示す。** センサスのレポートと追跡 issue の赤の行には、それぞれ、ケースとトライアル、観測された失敗と Expected/Received の値(判定の場合は、dimension、mean、samples、最も低い点の rationale)、トランスクリプトを保持する成果物、次の行動が示されます。次の行動は、まず無料で検査してリプレイすること、そして有料の実行は「修正の後に」だけ、そのケースだけを選んで行うことです。目標は、レポートの 1 行だけで診断できることで、赤 1 件あたり 5 分です(今は 15〜20 分)。公開 issue、PR コメント、コミット済みファイルに届くモデルまたはフィクスチャ由来の文字列は、一つのサニタイザーを通します。制御文字を取り除き、メンションを無効化し、コードフェンスはバッククォートの最長の連続より長くし、HTML をエスケープし、長さに上限を設け、リポジトリの認証情報スキャンのパターンを伏せ字にします(敵対的テスト: @mention、三連バッククォート、`</details>`、画像リンク、`ghp_`/`sk-` のトークン、10 KB の文字列)。
- **P3. 低い判定サンプルはすべて原因を持つ。** 最近のセンサスにあるワークフロー判定の低いサンプルは、それぞれスキルテキストの修正か、密度に関する不満のみとして記録されたものに対応づけられます。判定は、まず意図的に悪い対照バンドルで試し、そもそも識別できるかどうかを確かめます。
- **P4. このウェーブの小さなプロダクトの欠落を埋める。** (Bun の下限、make-pdf の `$P`、#2709 の reap、Codex の読み取り専用 `.git` の下での /review のフィンガープリント、design モデルのスモーク、定期の Codex ライブケース。)

### ワークストリーム 0(最初、無料): 証拠

- **0.1 セッション台帳、ヘッドルームレポート、赤の台帳。** ランナー(SDK、PTY、Codex)は、武装されたセッションごとに 1 行を、トライアルの成果物ディレクトリにある小さなセッション台帳ファイルに追記します(`contract-violations.jsonl` と同じパターン)。内容は、安定したセッションキー、武装したタイムアウトの正確な値、単調増加する経過時間、終了理由、そして簡潔な生存性の要約(リクエスト中の最長の無音、最後のイベントの種類、終了時に開いていたツール)です。レコードを作るビルダー(PTY と JUnit のみのケースを含む `junitCensus` を含む)は、トライアル記録にこの台帳を添付します。新しいモジュール(`eval-flake-rank.ts` ではない)が、ケースごとに次を報告します。武装された予算に対する経過時間(セッションごとに。ケースのヘッドルームは、最も遅いセッションによって決まる。タイムアウトしたサンプルは打ち切りとして印を付ける)、ランナーのスライスの所要時間からのレーンのクリティカルパス、マシンが分類した原因別の判定の赤とケースごとの率です。過去のセンサスにはセッションの時計がないため、履歴では、ケースの所要時間は上限であることを示すラベルを付けます。セッションのヘッドルームは、これが入った後の最初のセンサスから始まります。最小サンプル数を下回るケースは `insufficient` となり、決して合格にはなりません。利用方法は `bun run eval:pass-rates --headroom | --reds | --run <id>` で、オフラインの `--help`、未知のフラグと未知のケースの拒否、JSON とアラームに適用される `--case`、表示される run/branch のスコープがあります。`--run` は、赤の行が指す スライスだけをダウンロードします。すべて緑になる確率は、ケースごとに縮約された率の上の Π(1-p_i) で、区間付きで、近似であるとラベルを付けます(独立性は証明されていません)。
- **0.2 失敗原因の分類器(ポリシーに依存しない)。** 純粋で依存関係のない `failureCauseOf()` を `failureClassOf()` の隣に置きます(`e2e-helpers.ts` には置きません。そこは `bun:test` と選択の機構を import しています)。両方のレコードビルダーから、ランナーの観測とセッション台帳を使って呼ばれます。優先順位の契約は、contract > pre_turn_infra > api_error > refusal > provider_stall > session_timeout > observer_timeout > assertion > unknown です。`failure_class` は決して変えません。証拠が食い違う場合は、優先度の高い原因を採用し、両方を記録します。PTY でアイドル状態のターンに `API Error:` のパネルが表示された場合は、そのパネルの行を付けて `api_error` を記録します(PTY ランナーの `observe()` は既にそこで停止しています。他のランナーもマッチさせます)。拒否は、まず構造化された停止理由から検出し、フレーズは最後に使います。ストリームの停止は、セッションが部分的なメッセージをストリームしており、思考のデルタを含むどの種類のイベントも 120 秒間届かず(事前に登録した値です。Claude Code 2.1.284 で捕捉した 50 件のメッセージにわたる、メッセージ内の最長の無音は 9.6 秒でした)、かつモデルのリクエストが処理中で、ツール呼び出し、権限プロンプト、フック、サブエージェントのいずれも未完了の場合にのみ記録します。部分メッセージを使わないセッションは、決して停止として分類しません。部分メッセージは、このために有効にしますが、保持するのは簡潔な生存性の要約だけです(完全な診断はトランスクリプトのサイズをおよそ 4 倍にしてしまいます)。`panelVerdict` とレーンの判定は変えません。リプレイ: 37195203538(拒否)、37174266054 と 37176837432(タイムアウト)、37186854666(部分メッセージなしで実行されたため、`session_timeout` になる必要がある)。`provider_stall` の陽性例は、注入された無音を含む合成フィクスチャです。対照として、長い思考、ハングしたツール、権限待ち、フック実行中、サブエージェント実行中のトランスクリプトは `provider_stall` にはなりません。拒否のテキストを引用したツール結果は `refusal` にはなりません。ランナーごとに 1 件のフィクスチャ(SDK、PTY、Codex、JUnit)を用意します。

- **0.3 レポートと追跡 issue。** Expected/Received の値(今は `sanitizeTrialError` が最初の行だけを残すため、ウェーブの失敗 28 件のうち 16 件は有用な情報が何も表示されません)と、判定のスコアと rationale は、`error` ではなく `failure_detail` に入れます。すべての赤は成果物を名指しします。`rerun:` は「修正の後に:」に変わり、そのケースだけを選択します。週次の issue には、完全なパス率のアラーム行(今は grep によってヘッダーだけが残っています)、赤の台帳、すべて緑になる確率(誰でも再実行できるコマンド付きの文書化された式)を含めます。ブランチで dispatch されたセンサスは、main の追跡 issue に投稿したりクローズしたりしません(どちらの手順も `refs/heads/main` でゲートされ、evals-marathon.yml も同様です)。また、定期ワークフローの concurrency グループはブランチごとにスコープされ、ブランチのセンサスが main のものをキャンセルしなくなります。ブランチと run の識別子は、`git rev-parse --abbrev-ref HEAD` ではなく明示的に渡します。
- **0.4 「センサスが赤くなった」ガイド。** レポート、issue、CONTRIBUTING からリンクされる短いページです。前提条件、正確な検査とリプレイのコマンド、期待される出力、不明なデータが何を意味するか、そして有料の実行がいつ許されるか(修正の後のみ。TESTING_INTERNALS に従う)を書きます。永続的な証拠(ベースラインの赤の台帳、判定の診断)は `docs/evals/` にコミットし、一時的なものは `.context/` に置きます。

### ワークストリーム A: レポートが指摘するケースのヘッドルーム(P1)

- **A1. ship-docsync の完了(88%)と store(79%)。** まず保存されたトランスクリプトから診断します。親が リリースファイルの内容を読むことが支配的であれば、親はそれらを読むのをやめ、`bin/gstack-docs-candidate` でハッシュを再計算します(安価で、モデルによる読み取りはありません)。そして子が主張するハッシュと比較します。不一致は引き続き明確な失敗のままです。子の結果の契約を変更する場合は、パーサー、子、アクター、親をすべて一緒に更新し、ハッシュのアルゴリズムとファイルの集合を定義し、古い結果、欠けたファイル、報告されていない変更のネガティブケースを残します。
- **A2. plan-mode-no-op(432〜613 秒。おそらく 711 秒のクリティカルパスのゲートのスライス)と plan-ceo-mode-routing(687 秒)**: 保存されたトランスクリプトに対して時間を区切って調べ、まずフェーズごとの内訳(プリアンブル、Step 0、モデルの応答時間、ツールの時間)を報告します。その後、スキルまたはフィクスチャの作業を削ります。モデルの応答時間が支配的であれば、ワークフローを弱める削減ではなく、名前の付いた項目として扱います。
- **A3.** 0.1 のレポートが 75% を超えると示すその他のケース。review-army-perf と plan-design-review-plan-mode は、レポートがフラグを立てない限り作業はしません。
- **A4. 新規ユーザーのクリティカルジャーニー。** マラソンのレーンは、既存の新規 /plan-eng-review のケース(plan-eng-review-artifact-full)を PR のヘッドで実行します。最初の質問までの時間と、書かれたテスト計画までの時間を PR に報告します(ノンブロッキングのレーン)。新規の /ship のマラソンケースは、新しいハーネスの作業になるため TODOS に回します。
- 修正の前後の数値は、ローカルの実行からではなく、名前の付いた CI のセンサスから取ります。

### ワークストリーム B: 堅牢な検出器とアクター(最大の赤の分類)

- **B1. 繰り返し失敗するものへのリプレイ用コーパス。** shared-libs-plan-callers、plan-ceo-section-loading、auto-decide-preserved、plan-design-review-plan-mode、ship-docsync-late-result のそれぞれについて、保存された合格と失敗のキャプチャのうち、まだダウンロードできるものを、無料のスイートでその検出器またはアクターにリプレイします(各 1 件以上の合格と 1 件以上の失敗)。(まず棚卸しします。成果物は 30〜90 日で期限切れになり、期限切れのものは利用不可として一覧します。)エントリーは、最小限の、秘匿化された抜粋(検出器の入力スライス、サイズに上限があり、CI で認証情報をスキャン)で、由来する系列の識別子に紐づけます。古いエントリーは更新のためにレポートします。各コーパスエントリーは、元のセンサスの結果、期待される検出器またはアクターの結果、一行の正当化を記録します。そのため、修正された偽の赤は、履歴を残したうえで期待どおりの合格になり、本当のネガティブケースは引き続き拒否されます。
- **B2. フレーズより先に構造化されたシグナル。** スキルがすでに構造化されたレコード(決定の台帳、レビューのログ、ハンドオフのヘルパーの出力、`VERDICT:` の行)を書いている場合、有効な現在の構造化された証拠(正しいセッション、アクションの後、コピーされたフィクスチャの入力ではない)が決定的になります。フレーズの検出器は、構造化された証拠が存在しない場合にだけ実行します。ユーザーに見える出力(表示された質問、描画されたテキスト)が契約になっている場合は、行動の目撃記録は引き続き必要であり、レコードは場所を示すだけです。定期およびゲートのすべての検出器を監査し、フレーズだけによるチェックを探して、構造化されたソースがあるものは変換します。
- **B3. フロアランナーの TTY プレビュー**(TODOS の P2): `currentEditPreview` で、折りたたまれたコンテキストの行と、ガターのない折り返しを受け入れます。それでも正確なソース行と比較します。PR run 37176835584 の画面をリプレイします。
- **B4. `--case` でループに登録されたケースを選ぶ**(カバレッジの監査、TPA、plan-mode-no-op)。未知の ID は、プロセスを開始する前に非ゼロで終了します。
- **B5. シャードの隣接ケースの後ろでの pre-push フックのハング**: 失敗した計画を xvfb の下で再現し、まず診断します。原因がスコープ内にあれば修正し、そうでなければ名前の付いた未解決項目とします。

### ワークストリーム C: 判定(P3)

- **C1. 低いサンプルを出した判定にだけ、まず較正の対照を行う**(qa、qa-only、review、plan-ceo モード、plan-eng のセクション、必要に応じて setup-deploy)。4 での採点の圧縮は仮説であり、事実ではありません(スキーマは 5 を許容しています)。`docs/evals/` に、陽性、陰性、標的を絞った欠陥の対照バンドル、それぞれの期待される結果、判定ごとに 3 サンプルのパネル 1 件を事前登録します。`scripts/judge-calibration-configs.ts` を再利用します。判定が陰性の対照を区別できない場合は、そのケースを PR に「カバレッジを与えない」と列挙し、ルーブリックの提案を、事前登録された EVAL_POLICY の変更として Garry に持ち込みます。
- **C2. 低いサンプルの原因を追跡する。** 直近 N 回のセンサスにおけるすべての低いワークフロー判定サンプルの rationale を `.context/` に集めます。スキルのテキストは、rationale が具体的で実行に関係するギャップを指している場合にだけ修正します(観察可能な失敗がある場合はそれと結びつけます)。密度に関する不満だけのものは記録しますが、追いかけません。再生成し、パリティ、プロンプトのサイズ、削除された句のチェックを行い、変更した判定ごとに 3 サンプルのパネル 1 件を実行します。
- **C3. ドリフト中の行動ケース。** plan-review-prosons-neutral-neg(`eval:pass-rates` により ACTION REQUIRED とフラグ付け)と shared-libs-opportunity-judgment: 保存されたトランスクリプトから診断し、原因を修正します。診断が検出器、ハーネス、またはモデルの応答時間であり、CASE_QUARANTINE のエントリー規則を満たす場合にだけ、CASE_QUARANTINE のエントリーを提案します。
