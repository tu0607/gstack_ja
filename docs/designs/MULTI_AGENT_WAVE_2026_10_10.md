### リリースの約束(ゴール)

- **P1. インストールチェックは嘘をつけない。** 何もインストールされていないマシンで、1 つのコマンドがコンポーネントごとに PASS/FAIL の行を 1 行ずつ出力し、正確な修正コマンドを付けます。最後は `gstack: fail <components>` で終わり、非ゼロで終了します。健全なマシンでは `gstack: ok <revision>` で終わります。親エージェントは、その 1 行を grep することで、サブエージェントのマシンを確認します。計画専用のマシンでは Chromium をスキップします。
- **P2. /autoplan、プランレビュー、/cso は、Claude Code のハーネスがないホストで無人で実行されます。** 新しい `unattended` セッション種別では、フック、AskUserQuestion、Skill や Agent ツールを必要とせず、何も尋ねず、次のファイルを書き出します。`plan.md`、`review-record.md`、`tasks.jsonl`、`decisions.jsonl`、`findings.jsonl`、`timing.json`、そして `run.json` マニフェスト。これらはすべて、バリデーター付きの一つのバージョン管理されたスキーマに従います。親エージェントはプローズを読まずにこれを消費します。承認ゲートは決して自動承認されません。ゲートのリストとして書かれ、実行は終了します。
- **P3. 「ship、キュー内で次、バージョン <version>」が動く。** スタンプは PR が次になったときに押され、その時点の main の VERSION から、リポジトリ自身のリリースツールを持っている場合はそれを通して、すべてのスタンプ箇所に同時に適用されます。PR にはツリー同一性の受領証と、識別子を先頭に置いたハンドオフ記録が付きます。手作業のスタンプ編集はゼロです。ゲートされたツリーの純粋な再スタンプは、`gate-reuse: eligible` と報告されます。その根拠となる同一性は、ツリー(スタンプと生成パスを除く)、ランタイムの固定、ロックファイル、CI の設定です。調整役はそのゲートを再度支払うのではなく、再利用します。
- **P4. 安価なチェックは、有料またはリモートのゲートより前に実行されます。** 2 分の事前ゲートは、フィードバックにあるすべての機械的なドリフトの事例(古いゴールデンファイル、スクラッチファイル、パイプに隠れた失敗、実行されなかったプラットフォームのレーン、夜間限定テストの古い定数、落とされたベンダーのハンクを含む)を再生します。どれか一つでも失敗していれば、ゲートの開始を拒否します。
- **P5. プラン、レビュー、調査は、gbrain の教訓を必須の行として持ちます。** 各教訓は、それを生んだインシデントに紐づき、欠けていればレビューを失敗させます。
- **P6. 測定、調整、オーナーの視点に、第一級のサポートを提供します。** 予算台帳付きの事前登録評価のワークフロー、レーン所有権と証拠バンドルのツール、番号付きの決定事項を持つ 1 ページのオーナー向けブリーフです。
- **P7. 採用状況は推測ではなく測定します。** 耐久性のある記録媒体は、すでにマシンの外に出ているものです。マージされた PR 本文にある `run.json.consumed_by`(親が選んだ `--out` ディレクトリ内)と、ship 受領証の `session_kind` と `artifacts_consumed: <n>/<m>` のフィールドです。`gstack-ship-receipt census --repo <r> --since <tag>` は、マージされた PR から `gh` を通して、実行 ID とスレッド ID で重複を除き、オーナーが管理するスレッドのコホート(gstack を一度も呼び出さないスレッドも分母に含みます)に対して、その数を計算します。state-root の分析は、`durable=no` とラベル付けされたおまけとして残します。PR D と E の tier 3 の項目は、B-runner 上の最初の 10 件の Capy スレッドで、親が成果物を消費した無人実行が少なくとも 6 件見られた後にのみ始まります(UC1 を参照)。

### PR A: 正直なインストール(P0-1)

**A1. `gstack-doctor --check`: 一行の判定。** `bin/gstack-doctor` に `--check` モードを追加します。コンポーネントごとに 1 行、`PASS <component>` または `FAIL <component> — fix: <exact command>` を出力し、最後は `gstack: ok <revision>` または `gstack: fail <component,component>` で終わります。FAIL が 1 つでもあれば終了コード 1、必須のコンポーネントがすべて通ったときだけ終了コード 0 です。コンポーネントは次のとおりです: Claude スキル、Codex スキル、Astra の挙動パッチ(Capy インストーラーが今行っているように、生成されたパッチの見出しを grep)、browse バンドル、Chromium の起動と描画(setup の起動プローブを再利用し、`bin/gstack-render.ts` を通じた `setContent` のスモーク描画を加える)、ランタイムの固定、プライバシーの状態。準備完了かどうかは、要求されたワークフローに対して相対的に判断されます。`--for <skill>`(または `--require <csv>`)は、そのスキルが必要とするコンポーネントを指定します。計画系のスキルでは、両方のホストのプロファイルとパッチ。ブラウザ系のスキルでは、それに加えて browse バンドルと Chromium。`/cso` では、さらにネイティブヘルパー。トレーラーには、証明されたワークフローの名前が出ます(`gstack: ok 1.91.70.0 for=autoplan`)。どちらのフラグもなければ、必須セットはインストールされたホストになり、トレーラーがそう明言します。間違ったホスト、認証の欠落、互換性のないランタイムのフィクスチャは、ファイルの欠落だけでなく、テストされます。コンポーネントの表は一つだけで、それが行 ID、`--for` の解決、`--require`、トレーラー、`--json` のキーを供給します。そのため、親が語彙を対応づける必要はありません。doctor は Bash 3.2 のままで、Bun なしで報告します(bin/gstack-doctor:22。P1 のシナリオは、Bun が存在しないか、下限を下回るマシンです)。そのため、表の正とする情報源は `lib/doctor-components.ts` にあり、doctor が読み込むファイル `bin/gstack-doctor-components.sh` は、ビルド時にそこから生成されます。鮮度のテストも付け、agents のダイジェストと同じ方式にします。`--check` は、`bun` を `PATH` から取り除いた状態、インストール済みホストの集合が空の状態(決して `ok` にならない)、満たされない `--revision` の状態(決して `ok` にならない)で、フィクスチャされます。`gstack runtime` の行は、gstack のセキュリティ下限(1.3.3)と、サポートされる最低バージョン(1.4.2、bin/gstack-bun-version.sh:15)を区別します。1.3.14 は `--check` では FAIL です。`--for <skill>` は、行の前に `required: claude codex patch` を出力します。各行は `PASS | FAIL | SKIP <id>` の形式です。SKIP は、選択されたワークフロー、ホスト、ランナーが必要としないコンポーネント(`not_applicable`)、または存在しないオプションのコンポーネント(`optional`)を示します。外部の意見として Claude のサブエージェントを使い、Codex CLI のない健全な Capy マシンは、`--for autoplan` に合格します。`--json` は、同じ行をオブジェクトとして出力します。`--check` は、`--live` も渡されない限り、有料の Codex プローブを決して実行しません。沈黙の成功を不可能にします。すべての経路でトレーラーを出力します。`./setup --status` は、インストール行が壊れたセクションリンクを報告した場合、常に 0 を返す代わりに 1 で終了します(setup:136-146)。

- 新しい行: `gstack runtime`(gstack 自身の下限と、テストされたバージョンに対する Bun。今日の `bun` の行)と、`project pins`。`project pins` は、*対象リポジトリ*(`--project <path>` で指定。デフォルトは cwd の git トップレベル。gstack のチェックアウトではない)の `packageManager`、`engines`、`.tool-versions`、`.nvmrc`、`.bun-version`、および `.github/workflows/*.yml` 内の CI マトリクス(`bun-version:` / `node-version:`)を、新しい `lib/runtime-pins.ts` を通して読みます。実行中の Bun と Node と比較し、範囲(`>=1.4.2`)と厳密な固定値を区別し、有効な制約をそれぞれの出典とともに表示します。プラットフォーム固有の CI の固定値は、そのレーンとともに保持します。たとえば Windows のワークフローは Bun と Node を別々に固定しており(.github/workflows/windows-free-tests.yml:83)、Linux の実行をブロックしてはなりません。出力は次のとおりです: `FAIL project pins — bun 1.3.14 outside engines.bun >=1.4.2 (package.json:80; CI windows-free-tests.yml:89 pins 1.4.2); fix: bun upgrade --version 1.4.2`。プロジェクトの固定値に対する不一致は、`--check` では FAIL(固定されていないランタイムに対するゲートがこのインシデントです)、ダッシュボードでは `warn` です。`privacy` は `gstack-config get` から、`telemetry=<mode> artifacts_sync=<mode> codex_reviews=<v> update_check=<v>` を値だけ出力します(doctor のクランプ規則)。`cores` は CPU 数を出力し、8 コア未満であればリモートゲートを推奨します(E2 が使います)。

**B7. フィンディングから導出されるレビューログのステータス。** `reviewFreshness` は、未解決の問題を持つ `clean` の行を、読み取り時に UNVERIFIED へ降格させます(lib/review-evidence.ts:238-240)。ギャップは書き込み時にあります。`bindReview`(lib/review-evidence.ts:178-186、唯一のチョークポイント)は `--findings <path>` を受け入れます。そのファイルから `status`(フィンディングが一つも未解決でなければ `clean`、そうでなければ `issues_open`)、`unresolved`、`issues_found`、`critical_gaps` を導出し、主張された値と食い違う行を拒否します。行は、別々の `findings_total`、`findings_open`、`findings_resolved` を持ちます。`reviewFreshness`(lib/review-evidence.ts:238)は、同じ変更で `findings_open` を読むように更新されます。今日では、すべてのフィンディングが解決済みであっても、`issues_found > 0` の行を拒否しているからです。拒否された行は、stderr に `review-log: status mismatch: claimed clean, findings.jsonl has 176 open (REVIEW_STATUS_MISMATCH)` を出力して終了コード 1 で終わります。ラッパーは `2>/dev/null`(bin/gstack-review-log:95)を外し、バインディングの失敗を `invalid JSON` に変換しなくなります。使い方の誤りの終了コードは 2 になります(今日は 1。:81-84)。従来の `critical` と Codex のカウンターは、保守的な読み方を保ちます。`--findings` なしで書かれた行は `status_source: claimed` とタグ付けされます。無人の autoplan は、常に `--findings` を通してログします。フェーズのサブエージェントが JSONL を書けない場合、フィンディングを親に返します。親が `findings.jsonl` とログを書きます。`issues_found: 176` の隣に手書きされた `status: clean` は、書き込み時に拒否されます。

**B8. 上限での仕様レビューのループ。** このループは、PASS、繰り返される問題、または 3 回目の起動で停止します。スコアが欠けているだけでは、再度起動することにはなりません(scripts/resolvers/spec-review.ts:182-192)。1〜10 のスコアは報告されますが、停止のルールではありません。上限では、未解決のギャップを番号付きリストとして出力し、記録された 2 つの経路のどちらかを取ります。入力が変わっていないのに再サンプリングすることは決してありません。一つ目は、決定論的な問題検証のパスです。リストされた問題だけを、修正を適用した後にチェックします。`issues verified: k of N` として記録します。完全なレビューの判定に昇格させることは決してなく、上限を超えて四回目のモデル起動もしません(無人のデフォルト)。二つ目は、`N fixes unconfirmed` とし、承認ゲートを `spec not re-verified` という決定でブロックします。対話的なユーザーは `--max-rounds` を上げてもよく、その追加の各起動には、変化した入力のハッシュが必要です。`DONE_WITH_CONCERNS` は、スコアの隣に、欠けている点を常に明示します。

**B9. 四つの選択肢の連続の代わりに、一つのゲートリスト。** 新しい `lib/gate-list.ts` と `bin/gstack-gate`(`render`、`parse`)。ゲートリストは、番号付きの項目で、それぞれに推奨の既定値と、英字の選択肢があります。返答の文法は一つです。`all`(すべての項目が推奨を取る)、または `<id><option>` のトークン(`d3b uc1a`)、または `all except <tokens>`(すべての項目が推奨を取るが、挙げられた上書きは例外。二つの形式は同じ操作なので、除外と上書きの曖昧さはありません)。`yes`/`no` だけの返答は、複数の選択肢の項目にまたがるため曖昧として拒否され、解析されなかったものとして報告されます。すべての項目は安定した ID を持ち、ページ送りをまたいでも残ります(7 項目を超えるリストは、同じ ID のページに分けて描画されます)。項目は `auto`(未回答なら採用される)または `approval`(回答されるまで保留。オーナーの指示が優先)のいずれかにマークされます。返答はそれが応答するゲートのリビジョンに結びつき(`decisions.jsonl` の `gate_rev`)、古いリビジョンへの返答は、現在のリビジョンとともに拒否されます。描画されたリストは、受け付ける返答の正確な形式と、生成される解決済みの JSON を出力します。`parse` は、解決された選択を JSON として返し、推測せずに解析されなかったトークンを一覧にします。autoplan のフェーズ 4 は、対話的にも無人でも、ゲートをこれを通して描画します。CEO のステップ 0 のテイストの決定は、実行の途中で尋ねられる代わりに、同じリストに加わります。フィードバックで引用されたオーナーの返信(`d10 yes`、`1a 2a`、33 件の決定をまとめて承認)は、解析のフィクスチャです。

**B10. 壁時計時間と、実行前の見積もり。** `phase-close` は、フェーズの開始と終了、外部の声の壁時計時間、ネイティブの壁時計時間を `timing.json` と `$GSTACK_STATE_ROOT/analytics/autoplan-timing.jsonl` に記録します。フェーズ 0 は、プランのバイト数と検出されたスコープから、記録された履歴(フェーズごとの直近 10 回の実行の中央値。空なら `no history`)を使って見積もりを表示します。最終レポートは、実際の全サイクル時間を、その見積もりの隣に表示します。

**B11. 外部のパスがネイティブのパスと並ぶときの突き合わせ。** 外部の Bash ディスパッチは、ネイティブのレビュアーが走っている間に開始されることがあります(両方が同じスナップショットに結びつきます)。`phase-close` は、明示的な番号付きの操作を追加します。外部の各フィンディングについて、ネイティブの結果に対して `confirmed`、`disagree`、`new` のいずれかを記録します。Eng のディスパッチについては、送信前に、プロンプトに前のフェーズの合意の要約が存在することを確認します(CEO の要約が欠けたテストフィクスチャは拒否されます)。完了のバリアとフェーズの順序は変わりません。

- `regen`: `.gstack/generated.json` の各エントリが最新であること(C4。`git worktree` の使い捨ての中での `--check`。`node_modules` のあるツリーのコピーは決して使いません)。リポジトリの regen スクリプトの外にあるゴールデンファイルも、そこに挙げられていれば含みます。
