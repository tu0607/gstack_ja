1. **[重大度: Critical] ゲートの再利用が、変更された振る舞いを認証しうる。** C3 は、スタンプパスと生成ファイルのパス全体を除外しており、変更された生成プログラムやプロンプトが `same-modulo-stamps` の資格を得られてしまう。既存の証拠の実装も同様に、許可されたファイル名を比較するだけで、許可されたバイト単位の変更は比較していない([bin/gstack-evidence:505](/workspace/gstack/bin/gstack-evidence:505))。逆に、生のロックファイルのハッシュが同一であることを要求すると、バージョン書き込みツールがロックファイルのバージョン情報を更新するため、通常の npm の再スタンプが拒否されてしまう([bin/gstack-version-bump:486](/workspace/gstack/bin/gstack-version-bump:486))。許可される版数変換を狭く定義し、それ以外の生成バイトはすべて比較に含めること。宣言されたピンに加えて、実際のランタイムとコンテナの同一性、実行されたテストの選択も記録すること。変更された生成振る舞い、メタデータのみのロックファイルの変更、依存関係の変更を、それぞれ別々にテストすること。

2. **[重大度: High] 新規マシンのインストーラーが、修復の手順より前に失敗する。** A2 は、setup と doctor の後で Bun をアップグレードするが、Bun が存在しないか下限を下回っていると、setup はその場で終了する([setup:296](/workspace/gstack/setup:296))。Chromium をスキップしても、依存関係のインストールと完全なビルドはコールドパスに残る([setup:1808](/workspace/gstack/setup:1808))。そのため、計画だけを行う場合の TTHW は未計測のままである。setup の前にランタイムを事前確認し、用意すること。`jq` も明示的に確認すること。計画用のクリーンなインストールは、ブラウザのブートストラップとは別に計測すること。要求するリビジョンと、古いチェックアウトに対する明示的な対処法を追加すること。「再利用はするが pull はしない」では、サブエージェントごとに異なるコマンド契約が生じてしまう。

3. **[重大度: High] 準備状況の要件が、対応している外部の実行環境と矛盾している。** A1 は、計画のためにホストの両方のプロファイルと Astra パッチを要求する。一方 B3 は、API または別ファミリーのホストのサブエージェントを使い、Codex CLI なしで完全なワークフローを提供すると約束している。また A1 は `--for cso` に対してネイティブ・ヘルパーを必須にするが、B2 はその不在を任意の `SKIP` として扱っている。選択されたホスト、ランナー、モデル、ワークフローの能力に対して準備状況を定義し、`required`、`optional`、`not_applicable` を明示的に表現すること。Capy に Claude のサブエージェントを組み合わせた健全なインストールで、Codex がインストールされていない場合をテストし、そのワークフローに特化した正直な判定を要求すること。

4. **[重大度: High] ランタイムのピンのチェックが、誤った環境を修復しうる。** A2 は setup のために gstack のチェックアウトに入るが、doctor が対象プロジェクトをどう特定するかは指定していない。A1 は、プロジェクトの制約を、すべての CI のランタイム宣言と組み合わせている。それらの宣言はプラットフォームごとに異なる。Windows のワークフローは Bun と Node を別々にピンしている([windows-free-tests.yml:83](/workspace/gstack/.github/workflows/windows-free-tests.yml:83))。そのため、それらを普遍的なローカル要件として扱うと、Linux での計画実行がブロックされうる。明示的な `--project` と、ワークフローとレーンの選択を必須にすること。各有効な制約の出所を表示すること。互換性の範囲と、テスト済みの構成を区別すること。Bun を変更する前に競合を解決すること。gstack のランタイムと、対象プロジェクトの互換性のないランタイムを分離すること。

5. **[重大度: High] unattended の完全な呼び出し契約と、継続の契約が存在しない。** B2〜B4 は、エクスポート、プロンプトの表示、`--outside-model` などのフラグを導入するが、起動、フェーズのディスパッチ、終了、再開を担う実行可能なものを 1 つも特定していない。現在のスナップショット CLI が公開しているのは準備のための操作だけであり、unattended な実行機ではない([bin/gstack-autoplan-snapshot.ts:830](/workspace/gstack/bin/gstack-autoplan-snapshot.ts:830))。パッケージのバイナリが公開しているのは browse と make-pdf だけである([package.json:7](/workspace/gstack/package.json:7))。実行可能な親エージェントの一連の手順を定義すること。明示的なプロジェクト、入力、出力ディレクトリ、ランナー、期限、支出の上限を指定し、さらに `status`、決定の適用、`resume` の操作を加えること。受け入れ条件には、保留中のゲートへの回答と、完了済みの有償レビューを繰り返さない再開を含めること。

6. **[重大度: High] 約束されたタスクファイルは、計画を読む代わりにはならない。** B2 は今日のタスクのスキーマを維持するが、そのスキーマにはタイトル、ファイル、自由記述の出典の指摘は含まれるが、検証コマンド、依存関係、受け入れ基準が欠けている。人間向けの形式では検証が含まれているにもかかわらずである([tasks-section.ts:42](/workspace/gstack/scripts/resolvers/tasks-section.ts:42)、[tasks-section.ts:77](/workspace/gstack/scripts/resolvers/tasks-section.ts:77))。ID はフェーズ内に限られる(`T1`、`T2`)。また B2 の指摘フィールドには、後に B12 で必要となる指摘 ID が明示的に含まれていない。実行ごとに一意な ID、タスクの依存関係、受け入れチェック、指摘の参照、ブロックする決定の参照を定義すること。参照の整合性を検証し、各レビュアーの不変の結果をマニフェストに結びつけること。モデルが書いた件数を照合しても、指摘が省略されていないことは証明できない。

7. **[重大度: High] 「機械可読性優先」には、共通の伝送契約がない。** A1 は JSON の行と、常に必須のテキストの末尾行を混在させる。B2 は空白で区切られたパスを出力する。C5 は Markdown のフェンスを提供するが、そのペイロードのエンコーディングを指定していない。C3 はテキストの判定を提供し、JSON のインターフェースがない。親は別々のパーサーを自作しなければならず、スペースを含むパスは単純なトークン抽出をすぐに壊す。共通の結果エンベロープと終了コードの表を要求すること。`--json` の下では stdout には JSON のみを出力し、診断は stderr に出すこと。`gate_pending` と `incomplete` の状態を明示すること。機械可読な回復のアクションを用意すること。新しいコマンドすべて(gate、restamp、regen、pregate、receipt、lane-check、hermetic-run、banned-terms のツール)に、発見可能な `--help`、引数の所有関係、テスト済みの `jq` の例を与えること。

8. **[重大度: High] 永続的な状態が、親と子の境界を越えて維持されない。** A3 は、インストーラーが `GSTACK_STATE_ROOT` を「設定する」と述べるが、子のシェルの export は、後から親が起動するコマンドには設定されない。リゾルバーは、各プロセスに与えられた環境だけを参照する([lib/state-root.ts:22](/workspace/gstack/lib/state-root.ts:22))。B2 はさらに、成果物を `ACTIVE_PLAN` の隣に書き込む。`ACTIVE_PLAN` は、永続的な状態ルートがあっても、一時的なストレージに残りうる。機械可読な起動設定を返し、親がそれを明示的に渡すようにすること。永続的な実行出力ディレクトリを必須にすること。成果物の種類ごとに、永続性を個別に報告すること。マニフェストのハッシュに結びついた、冪等な消費の確認コマンドを追加すること。さもないと、P7 の採用のしきい値が、文書化されていない報告に依存することになる。

9. **[重大度: High] キューの並べ替えに、権威ある版数の選択ルールがない。** C2 は `--next` を、任意の主張されたキュー上の PR の最高バージョンを超えて進めるアロケーターに委ねている([bin/gstack-next-version:97](/workspace/gstack/bin/gstack-next-version:97))。これは「この PR が次のとき、main のバージョンに 1 を加える」と矛盾する。先行 PR の head を確認しても、並べ替えの後もそれが先行 PR のままであることや、スタンプと検証の間にベースが変わっていないことは確認できない。期待するベース SHA、キューの順序、先行 PR の同一性、要求バージョンの意味論を持つ、明示的な stamp-at-merge の割り当てモードを導入すること。マージの直前にこれらの期待値を再検証し、古いキューの結果を、正確な再計算コマンドとともに構造化して返すこと。

10. **[重大度: High] マシンをまたぐゲートの再利用が、移植可能な証拠より先に来ている。** C3 は、使い捨てのマシンで実行されたゲートの再利用を約束するが、移植可能なバンドルは E2 にならないと現れない。既存の証拠は、マシンに局所的であることが明示されている。また、記録された各ラベルを確認しても、必要なすべてのレーンが実行されたことは証明されない([bin/gstack-evidence:27](/workspace/gstack/bin/gstack-evidence:27))。C5 の集計カウントも、この隔たりを埋めない。名前付きの必須レーン、実行された選択、元の実行の URL、結果、成果物のハッシュを含む、最小限の移植可能な証拠パッケージを C に移すこと。ゲートの VM を削除した後、ゲートを再実行せずに、新しいコーディネーターのマシンから検証すること。

11. **[重大度: High] 再スタンプは、チェックと適用の意味論が互換でなく、回復のトランザクションもない。** C2 は、生成器に変更されたスタンプの出力を要求する。一方 C4 は、変更された生成出力を古いものと分類するために、すぐに `git diff --exit-code` を使う。基礎となるバージョン書き込みツールには、部分的な書き込みの失敗の状態がすでにある([bin/gstack-version-bump:489](/workspace/gstack/bin/gstack-version-bump:489))。リリースフック、CHANGELOG の書き換え、ミラーを追加すると、「同じバージョンなら何もしない」では対処しきれない失敗の境界が増える。`regen --check` と `regen --write` を分離し、リリースツールのインターフェースを 1 つに定め、各再スタンプの意図した入力と完了した書き込みを記録するジャーナルを用意すること。無関係な編集を保ったまま再開・ロールバックできるようにし、各段階の後に障害を注入してテストすること。

12. **[重大度: High] ベースにしかないピンファイルには、最初の利用のためのワークフローがない。** C1 は、ベースブランチから実行可能なポリシーを読む。そのため、`.gstack/generated.json` や最初のリリースコマンドを導入する PR は、その宣言を使って自分自身を検証できない。実行権限があってもである。さらに、ベースで宣言された `bun run release:restamp` は、依然として PR のパッケージスクリプトを実行する。そのため、コマンドの文字列をピンしても、その実装は固定されない。既存のバージョン書き込みツールは、対象リポジトリのコードの実行を明記している([bin/gstack-version-bump:374](/workspace/gstack/bin/gstack-version-bump:374))。ポリシーの初期化、検証、有効な設定の確認を追加し、ソースのリビジョン、コマンド、作業ディレクトリ、信頼の範囲を表示すること。新しいポリシーのための、レビュー済みの明示的なブートストラップの経路を定義すること。単独実行、ship からの実行、ポリシー変更時の振る舞いをテストすること。

13. **[重大度: High] 2 分の事前ゲートは、YAML に含まれない CI の情報を前提にしている。** C8 はワークフローからのレーン検出を約束するが、このリポジトリでは Windows のマトリクスをプランナーを実行して計算しており([windows-free-tests.yml:62](/workspace/gstack/.github/workflows/windows-free-tests.yml:62))、排他的なテストの分類は TypeScript で定義されている([scripts/test-free-shards.ts:243](/workspace/gstack/scripts/test-free-shards.ts:243))。影響を受けるテストをすべてローカルで実行すると、2 分を超えることもある。超過を表示するだけでは、約束された高速なフィードバックは保てない。有界な機械的事前確認と、必須のテスト実行を分離すること。ランナーが所有する選択マニフェストを利用すること。選択の出所と不確実性を示す `--explain` を用意すること。リモートの要件には、ディスパッチするワークフローとジョブの名前、およびそれを解除するために必要なレシートを明記すること。

14. **[重大度: High] オーナーのゲートが、決定事項を隠したり、承認を誤解したりしうる。** E3 はブリーフを 7 件の決定に制限しているが、この計画では 12 件として提示されている。また、超過時の振る舞いは定められていない。さらに、B1 の保留中の承認の意味論と、UC1 の「オーナーの方向性は有効のまま」という指示に反して、未回答の項目に既定値を約束している。B9 は `all except d9b` を、除外なのか上書きなのか曖昧なままにしている。また、ベアの `yes`/`no` では、複数の未決定または複数選択肢の決定のうち、どの選択肢かを特定できない。ページ送りをまたいで、安定した決定 ID をすべて保持すること。自動的な選択と、必須の承認を明示的に区別すること。返信をゲートのリビジョンに結びつけること。期待される解決後の JSON とともに文法を定義し、曖昧なエイリアスは拒否すること。未回答の承認は保留のままにすること。

15. **[重大度: Medium] 指摘から導出されるステータスが、既存の鮮度チェックとエラー処理と衝突する。** B7 は `clean` と `issues_found` の両方を導出する。しかし現在の鮮度のリーダーは、ステータスが clean であっても `issues_found > 0` であればレビューを拒否する([lib/review-evidence.ts:238](/workspace/gstack/lib/review-evidence.ts:238))。また、提案されている詳細な不一致エラーは、シェルのラッパーに飲み込まれる。ラッパーは stderr を抑制し、束縛の失敗を「無効な JSON」として終了コード 1 に変換してしまう([bin/gstack-review-log:88](/workspace/gstack/bin/gstack-review-log:88))。総数、未解決数、解決済み数を別々に定義すること。リーダーとライターを同時に更新すること。ラッパーを通じて型付きのエラーを保持すること。多数の指摘があり、すべて解決済みのレビューをテストすること。

16. **[重大度: Medium] 各マージゲートが何を要求するかが、階層化で定義されていない。** C2 はミラーとゲート先行のサポートを tier 2 としているが、検証 3 では、PR C のキューの再生でその両方を要求している。また、tier 2 の作業を「次の PR」に移す方針と、別のフォローアップとする方針が交互に現れる。E2 と E3 には、すべての項目に階層があるという主張にもかかわらず、明示的な階層がない。機能、PR、階層の対応表を公開すること。その表には、コマンド、成果物の能力、延期された依頼を含めること。オーナーのゲートは、この具体的な表を承認すべきである。また、インストールされた各リビジョンは、実際に出荷された能力を公開すべきである。

ペルソナの追跡:

- **親の Capy エージェント:** (1) ブートストラップが Bun の修復の前に止まるか、予期しない完全ビルドを行う(#2)。(2) 準備状況に無関係なホストやランタイムのピンが要求される(#3〜4)。(3) 親が起動と継続の接着コードを自作しなければならない(#5)。(4) 消費を確認する前に、成果物の参照、保存場所、パーサーの違いを解決しなければならない(#6〜8)。**推定 TTHW:** 最初の有効な `gate_pending` のバンドルを得て消費するまでに、手作業の統合を伴って 45〜90 分。仕様どおりでは、unattended での完了に有界な経路がない。
- **キューのコーディネーター、3 つの PR が 2 回並べ替えられる:** (1) 有効なポリシーを確定する(#12)。(2) 次の PR を選び、要求されたバージョンと割り当てられたバージョンを照合する(#9)。(3) 再スタンプを行い、生成器やミラーの失敗から回復する(#11)。(4) 古いマシンからゲートの証拠を取り出し、並べ替えの後ごとに再利用を確立する(#1、#10)。**推定 TTHW:** オーケストレーションに 30〜60 分、加えてゲート 1 回の実行時間。並べ替えのたびに 15〜30 分の追加がかかり、証拠が利用できない場合は完全な再実行になりうる。これらはレビュー上の見積もりであり、計測された実行ではない。
